## 1. 자외선지수가 포털 검색값과 다르다

### 증상

카카오톡 알림의 자외선지수가 네이버·기상청 포털에서 검색한 값과 다르게 나온다. 항상 다른 것도 아니고, 어떤 시간대에는 맞는다.

### 가설

1. API 응답 자체가 포털과 다른 관측소/모델을 쓴다?
2. 우리가 응답에서 **엉뚱한 시각의 값**을 고르고 있다?

### 검증

기상청 UV API의 원본 응답을 열어 보면 값이 `h0, h3, h6, …` 필드로 온다. 이 이름은 시각이 아니라 **발표시각으로부터의 오프셋(시간)**이다. 즉 06시 발표분의 `h6`은 "06시의 값"이 아니라 **12시의 예보값**이다.

기존 코드는 이 구분 없이 앞쪽 필드를 집었고, 그 결과 아침 발표분이 들어온 오후에는 실제보다 이른 시각의 값이 나갔다. 포털은 최신 발표분의 현재 시각 값을 보여주므로 차이가 났다.

### 원인

`h*` 오프셋을 실제 예보시각으로 환산하지 않고 사용.

### 조치

발표시각(`base_time`) + 오프셋으로 각 필드를 실제 예보시각으로 풀고, **현재 시각 이하의 가장 최근 값**을 고른다. 전부 미래라면(새벽) 가장 이른 예보를 쓴다. `"-"`·`""` 같은 결측 마커는 후보에서 제외한다. — `producer/producer.py`의 `_select_latest_hourly_value`

### 후속편 — 같은 코드가 타임존 정리에서 다시 깨질 뻔했다

전 구간을 KST aware datetime으로 통일할 때([#39](https://github.com/hyeongyu-data/air-quality-project/issues/39), PR #65), `now`는 aware가 됐는데 `strptime`으로 파싱한 발표시각은 naive라 비교 시점에 `TypeError: can't compare offset-naive and offset-aware datetimes`가 났다. 자외선 선택이 통째로 죽는 회귀였고, TZ=UTC 환경에서 스모크를 돌려 잡았다. 발표시각도 `to_kst()`로 aware화해 해결.

### 재발 방지

- `tests/test_api_contract.py::test_uv_hourly_selection_skips_blank_markers` — 오프셋 환산·결측 마커·경계 선택을 픽스처로 고정
- `tests/test_timeutil.py::test_aware_and_naive_can_be_compared_after_conversion` — naive/aware 비교 회귀
- README의 "자외선지수가 포털 검색값과 다를 때" 항목에 남는 차이(관측소·발표 지연·보정 모델)를 명시

## 2. 황사 API 권한이 없다 → 대체값 설계 → 그 대체값이 거짓말이었다

### 증상

에어코리아 황사 발생정보 API가 401/403을 반환한다. 공공데이터포털에서 이 API는 별도 활용 신청 권한이 필요했다.

### 1차 조치 (그리고 그것이 만든 더 나쁜 문제)

"황사와 미세먼지는 상관이 있으니" PM10 평균을 황사 값으로 대체했다(`yellow_dust_source: "pm10_proxy"`). 겉보기에는 황사 지표가 계속 동작했다.

넉 달 뒤 진단([#44](https://github.com/hyeongyu-data/air-quality-project/issues/44))에서 이 대체가 **거짓말**이었음이 드러났다.

### 검증

황사 판정의 "좋음" 임계는 150㎍/㎥다(황사는 수백 단위 현상이라 척도가 크다). 서울 PM10 **평균**이 150을 넘는 날은 사실상 없다. 즉:

```python
# tests/test_dust.py — 프록시가 왜 무의미했는지를 테스트로 고정
@pytest.mark.parametrize("pm10_mean", [0, 10, 30, 45, 80, 120, 150])
def test_pm10_range_always_maps_to_good_dust(pm10_mean):
    assert E.classify_dust(pm10_mean)[0] is L.GOOD      # 항상 "좋음"
    if pm10_mean > 30:
        assert E.classify_pm10(pm10_mean)[0] is not L.GOOD   # 같은 값이 PM10 기준으론 나쁨
```

**감시되는 것처럼 보이지만 아무것도 감시하지 않는 지표**였다. 병합 조건의 버그로 발생정보 API가 정상일 때도 프록시가 덮어쓰고 있었다.

### 원인

서로 다른 척도의 지표를 값으로 이어 붙임. "모른다"를 그럴듯한 숫자로 바꾸면 결측보다 나쁘다.

### 조치

프록시 제거(PR #66). 권한이 없으면 결측(`None`)으로 두고, 컨슈머가 `정보없음` 등급으로 표시하며 행동 권고를 활성화하지 않는다. 임계값을 프록시 척도로 재보정하는 안도 검토했지만, 그러면 황사 등급이 미세먼지 등급의 복제가 되어 중복 지표가 된다 — 정직한 결측이 낫다.

### 재발 방지

- `tests/test_dust.py` 8개 — 프록시의 무의미성 자체를 테스트로 박제
- 결측 일반 원칙은 [#33](https://github.com/hyeongyu-data/air-quality-project/issues/33)의 `UNKNOWN` 등급 체계로 통일 (`tests/test_missing_values.py`)
- 판정 근거는 [ADR-0004](adr/0004-why-rule-engine.md) — "규칙 엔진에서 실제로 어려웠던 것" 절

## 3. 같은 알림이 반복해서 온다 → 쿨다운 → 그 쿨다운이 알림을 영구히 삼켰다

### 증상 (1편)

미세먼지가 "나쁨"으로 유지되는 날, 실행 시각마다 같은 내용의 카카오톡이 반복해서 왔다.

### 조치 (1편)

수치가 아니라 **등급 조합의 시그니처**(`pm10=나쁨|pm25=보통|…`)를 직전과 비교해, 바뀌었을 때만 외부 발송한다(#15). 수치 변동(82→85)에는 둔감하고 등급 변화에만 민감하다. 직전 상태는 재시작에도 살아남도록 OpenSearch에서 읽고, 조회 실패 시에는 유실보다 중복을 택해 발송한다(fail-open).

### 증상 (2편) — 쿨다운이 만든 더 나쁜 침묵

진단([#34](https://github.com/hyeongyu-data/air-quality-project/issues/34))에서 발견: 발송 결과와 무관하게 시그니처가 저장되고 있었다. 카카오 토큰이 만료된 순간의 등급이 "이미 알린 등급"으로 굳어, **등급이 유지되는 동안 알림이 영영 오지 않는다.** 채널을 복구해도 마찬가지다.

실제로 카카오 refresh token 만료(KOE322)로 이 경로를 그대로 재현했다 — 발송 실패 → 그런데도 다음 회차부터 "등급 무변경 → 생략".

### 조치 (2편)

"알렸다"의 정의를 **외부 채널 최소 1개 성공**으로 바꿨다(PR #59). 전량 실패 시 시그니처를 기록하지 않아 다음 회차에 재시도한다. 이력 문서 자체는 남기되 `delivered_channels`·`signature_recorded`를 함께 저장해 사후 추적이 가능하다.

### 증상 (3편) — 남은 두 구멍

1. 직전 시그니처를 이력 인덱스 **검색**으로 읽어, 직전 문서의 refresh(1초)보다 조회가 빠르면 중복 발송(백로그 연속 처리 시).
2. 등급이 오래 유지되면 무한 침묵 — 사용자는 "조용한 게 정상인지 파이프라인이 죽은 건지" 구분 불가.

### 조치 (3편)

지역별 **상태 문서**(`weather-cooldown-state`, 문서 ID=지역)로 이관(PR #77). 문서 GET은 refresh와 무관하게 실시간이라 레이스가 구조적으로 사라진다. 여기에 `last_external_send_at`을 함께 저장해, 등급이 같아도 12시간 무발송이면 한 번 재발송한다(`MAX_SILENCE_HOURS`). 생략 회차가 이 시각을 갱신하면 간격이 영영 차지 않으므로 **실제 전달 시에만** 갱신한다.

### 재발 방지

- `tests/test_cooldown.py` · `test_delivery_gate.py`(실패→미기록→재발송 3회차 시나리오) · `test_cooldown_state.py`(생략 회차의 last_sent 유지, GET 경로 확인)
- OpenSearch 미가용 시의 동작은 로컬 캐시 폴백으로 별도 방어(PR #70, `tests/test_opensearch_state.py`)
