# ADR-0003. 왜 OpenSearch인가 — 이력 저장과 상태 저장을 겸한다

- 상태: 채택 (2026-07-30)
- 관련 이슈: [#52](https://github.com/hyeongyu-data/air-quality-project/issues/52)

## 맥락

OpenSearch의 실제 용도는 두 가지다.

1. **판정 이력 저장** — 회차별 판정 결과 문서(`weather-alert-YYYY.MM`, `_id = event_id`). 하루 4건.
2. **쿨다운 상태** — 지역별 직전 등급·마지막 발송 시각(`weather-cooldown-state`, 문서 GET은 실시간이라 레이스 없음. #42).

정직하게 말하면 이 데이터량(연 1,460건)에 검색 엔진은 과하다. SQLite 한 파일이면 두 용도 모두 감당한다.

## 실제 도입 이유

1. **이력의 탐색 가능성** — "지난달 미세먼지 나쁨이 며칠이었나", "채널별 발송 실패가 언제 몰렸나" 같은 질문을 별도 코드 없이 REST 쿼리로 답할 수 있다. 운영 대시보드(#24)의 저장소가 이미 준비돼 있는 셈이다.
2. **컨테이너 간 공유 상태** — 쿨다운 상태는 Consumer 재시작·재생성을 넘어 살아남아야 한다. 파일(SQLite)로 하려면 볼륨 공유가 필요하고, 그러면 결국 "네트워크로 접근하는 상태 저장소"를 원하게 된다.
3. **학습** — 인덱스 템플릿, 동적 매핑의 함정(첫 문서가 int면 long 고정 → 45.6이 45로 절삭), 단일 노드 replica 미할당, ISM 보존 — 전부 이 프로젝트에서 실제로 부딪히고 고쳤다(#37).

## 검토한 대안

| 대안 | 탈락 이유 |
| --- | --- |
| **SQLite** | 상태 저장에는 충분하나 이력 탐색·시각화가 코드 작성으로 바뀐다. 컨테이너 간 공유에 볼륨 결합이 생긴다 |
| **PostgreSQL** | 상태+이력 모두 감당하고 운영도 익숙하지만, 검색·집계 API와 대시보드 스택(OpenSearch Dashboards)이 공짜로 따라오지 않는다 |
| **Redis** (상태 전용) | 상태에는 최적이나 이력이 해결되지 않아 저장소가 2개가 된다 |

## 결정

OpenSearch 하나로 이력과 상태를 겸한다. 저장소를 하나 더 들이는 것보다 이미 있는 것의 함정을 제대로 다루는 쪽을 택했다.

## 트레이드오프

- 힙 1GB — 이 데이터량 대비 명백히 무거운 상주 비용이다. 로컬 학습 환경이라 감수한다.
- 쿨다운 상태처럼 "절대 잃으면 안 되는" 값의 저장소로 검색 엔진은 이상적이지 않다. 로컬 파일 캐시를 이중화로 뒀다(#37).
- 보안 플러그인이 꺼져 있다 — 로컬 전용 구성이며, 운영 프로필 분리는 #20에서 다룬다.

## 재검토 조건

- 실배포에서 관리형으로 갈 때 → 이력은 그대로 OpenSearch(AWS OpenSearch Service), 쿨다운 상태는 DynamoDB 같은 KV로 분리하는 편이 맞다.
- 대시보드 요구가 끝내 생기지 않으면 → SQLite로 강등하는 것이 옳은 결정이 된다. 그 시점에 이 문서를 갱신한다.
