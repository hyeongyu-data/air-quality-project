데이터 품질

결측은 0이 아니다

결측을 0으로 치환하면 "체감온도 0℃ → 동상 위험"이 한여름에 발송되고, 미세먼지 결측이 "외출 자유"가 됩니다. UNKNOWN 등급을 분리해 결측은 판정·발송에서 제외하고 "정보없음"으로 정직하게 표시합니다.

rules.py · 판정 공통 경로 한 곳에서 9개 지수 커버
전달 보증

실패를 성공으로 기록하지 않는다

발송이 전량 실패하면 쿨다운 시그니처를 기록하지 않아 다음 회차에 재시도합니다. 그러지 않으면 SMTP·토큰 만료 순간의 등급이 "알린 것"으로 굳어 알림이 영구 유실됩니다. 수집 실패·발행 0건은 DAG 태스크 실패로 올라가 Slack으로 통보됩니다.

should_record_signature() · on_failure_callback
멱등성

키는 벽시계가 아니라 스케줄 슬롯에서

event_id = 지역:YYYYMMDDHH를 실행 예정 시각에서 만들어 재시도에도 값이 같습니다. Kafka는 멱등 프로듀서, OpenSearch는 _id upsert — 같은 이벤트를 3번 재처리해도 문서는 1건입니다.

상태 관리

쿨다운 상태는 문서 GET으로

직전 등급·마지막 발송 시각을 지역별 상태 문서로 관리합니다. 문서 GET은 refresh와 무관하게 실시간이라 검색 기반의 지연 레이스가 구조적으로 없습니다. 등급이 같아도 12시간 무발송이면 재발송해 "조용함 = 정상"을 보증합니다.

weather-cooldown-state · OpenSearch 장애 시 로컬 캐시 폴백
시간대

컨테이너 TZ에 의존하지 않는다

모든 시각을 코드에서 KST로 명시합니다(now_kst()). TZ=UTC 환경에서도 발표시각 역산·오늘 예보 필터·인덱스 날짜가 전부 같은 결과 — AWS Lambda(UTC 기본)로 옮겨도 조용히 틀어질 지점이 없습니다.

timeutil.py · TZ 3종 매트릭스 테스트
보안

키는 로그에도 페이로드에도 없다

공공 API 키는 쿼리스트링이라 예외 문자열에 그대로 실립니다. 값이 만들어지는 지점에서 마스킹하고, 로깅 필터를 안전망으로 겹칩니다 — 로그뿐 아니라 Kafka 페이로드·이메일 본문으로 새는 경로까지 막습니다.

기술 선택 — 왜 이 스택인가

규모 주장을 하지 않습니다. 과잉은 인정하고 근거와 재검토 조건을 기록합니다

선택정직한 전제실제 근거재검토 조건
Kafka 하루 4건 — 규모로는 정당화되지 않는다 수집과 발송의 장애 격리, 백로그 재생, 컨슈머 그룹·오프셋·멱등 프로듀서를 운영 문제로 학습 실배포 시 SQS 교체
OpenSearch 연 1,460건에 검색 엔진은 과하다 이력 탐색(REST 쿼리)과 컨테이너 간 공유 상태의 겸용, 매핑·ISM·단일 노드 함정 학습 대시보드 요구가 없으면 SQLite 강등이 옳다
규칙 엔진 ML을 쓰지 않는 이유를 물을 지점 임계값이 환경부·기상청 공인 기준 — 가치는 예측이 아니라 기준의 정확한 반영과 설명 가능성 자체 예측 요구 시 모델을 입력 지수로 추가
로컬 Docker 비용 절약이 아니라 검증 가능성의 선택 모든 코드가 docker compose up으로 제3자 재현 가능. 검증 불가한 AWS 코드는 삭제(ADR-0001) 실사용자 상시 제공 시 EventBridge+Lambda+SQS

운영 품질

전부 Docker에서 장애를 실제로 일으켜 검증한 항목입니다

  • 재생성 내구성Kafka 토픽·오프셋, Airflow DAG 상태·이력, OpenSearch 데이터가 docker compose down/up을 넘어 유지 — 볼륨 소유권 함정(non-root vs root 생성)을 실측으로 회피
  • 장애 복원브로커·OpenSearch가 죽은 채 기동해도 지수 백오프(5→300초)로 스스로 재연결. OpenSearch 중단 중에도 로컬 캐시로 쿨다운 유지
  • 수명 관리SIGTERM 1초 내 정리 종료(exit 0), 하트비트 파일로 "프로세스 생존"이 아니라 "루프 생존"을 healthcheck
  • 보존 정책Kafka 72h · OpenSearch ISM 90일 — 무한 증가하는 저장소가 없다
  • CI 게이트compile + 143 테스트가 머지 필수 조건(브랜치 보호). 패키지 import 스모크로 "CI 초록인데 런타임 완파"류 재발 방지
  • 협업 프로세스Issue → 브랜치 → PR → CI → squash. CODEOWNERS · 보안 체크리스트 템플릿 · Dependabot 7일 SLA
  • 결정 기록ADR 5편 — 전부 검토한 대안과 재검토 조건 포함. 장애 시나리오는 운영 리스크 문서에 파일:라인 근거로

엔지니어링 과정

이 저장소의 차별점은 완성된 코드가 아니라 결함을 다룬 방식입니다

진단부터 했습니다. 데이터 엔지니어링 실무·플랫폼 아키텍처·SRE·채용, 네 관점으로 독립 검토해 결함 28건을 심각도별로 등록했습니다. 그중에는 "API 장애 시 결측이 0이 되어 한여름에 동상 경고가 나간다", "발송이 실패해도 성공으로 기록돼 알림이 영구 유실된다" 같은 P0 6건이 있었습니다.

의존 순서로 고쳤습니다. 거짓말을 멈춘다(오알림·실패 은폐) → 상태를 잃지 않는다(영속성·멱등성) → 측정할 수 있게 만든다 → 회귀를 막는다 → 근거를 남긴다. 순서를 뒤집으면 잘못된 데이터를 성실하게 영속화하게 됩니다.

전부 실측으로 검증했습니다. 볼륨 소유권은 컨테이너를 띄워 확인했고, 장애는 실제로 일으켰고(OpenSearch 중단, stale pid 재현), 회귀 테스트는 18개에서 143개가 됐습니다. 검증할 수 없는 코드(실행된 적 없는 AWS Glue 메달리언)는 근거를 ADR로 남기고 삭제했습니다 — 검증 불가능한 코드를 두지 않는 것도 설계 결정입니다.

이 문서는 저장소 docs/dashboard.html로 관리됩니다. 숫자(테스트·PR·이슈)가 바뀌면 상단 지표를, 설계가 바뀌면 해당 카드와 ADR 링크를 갱신합니다.
